How the analysis was run, and what the audit found

The findings stand on their own on the analysis page. This page is the machinery behind them: the three commands that produced the results, the guard rail that refused a cheating model, and the three defects I found while testing it.

Prateek Sharma · Avaloka Engineering Intern Hackathon · open-source CLI, $0, no API key, 0 LLM tokens

1What the tool actually did

Three commands, three different jobs. None of them called an LLM: the whole run is deterministic and offline.

CommandQuestion it answersWhat it produced here
analyzeWhat is in this data?Three grouped reports (by job type, fallback route, task domain) + data-quality profile
trainCan we predict the answer?A validated router, 0.956 holdout, level 4/4, plus a FastAPI service and Dockerfile
coordinateCan the work be split?Four sub-runs of 500 rows each, merged into one result, all shards passing

2The guard rail, in one example

The reason the router score is believable is not the score. It is that the same pipeline refuses a good-looking one.

It caught me cheating. I added one column collected after the call (post_call_route_flag) that simply encoded the answer. The claimed score jumped to a perfect 1.0000 — and the run was rejected: verdict FAIL, the leaking column named in the output, deployment capped at 1/4. The clean model, using only pre-call features, stayed at 0.956 and level 4/4. A perfect score on a real problem is a bug, not a triumph.

3The engineering audit

Reproducible with python scripts/03_reproduce_edge_cases.py: four of four contract checks hold, one declared gap reproduced, and two further defects found by hand. Full write-up with root causes and patches in audit/ENGINEERING_AUDIT.md.

What held

ProbeDeclared asResult
A post-call feature that encodes the target fails trainingDQ-01pass
The winner is compared with a trivial baselineDQ-05pass
An unresolved measure is disclosed, not counted#475pass
A null-like word stays a category#474 / #479pass

What didn't

ProblemDeclared?Result
The verdict never checks whether the question was answeredno — minemissing check
A sheet is chosen by cell count, not by the questionyes, xlsx_decoy_sheetreproduced
The sizing line says 99 rows for a 400-row sheetno — minereproduced
The verdict has no word for “I did not answer you.” Ask something the data cannot answer and the bundle returns two verdicts at once. goal_analysis.json reports status: "limited" — literally “not an answer to the question”. Beside it, validation_report.json reports verdict: pass, having run one check: data_sufficiency. The validator has eight check types — data_sufficiency, target_leakage, split_validity, beats_baseline, stability, overfitting, latency_budget, data_quality — and every one asks “is this result safe?”. None asks “did we answer the question?”. The status is already computed at analysis_planner.py:148; nothing reads it. Five lines in validator.py would close it.
Two wrong numbers from one run. The workbook reader chose a sheet by non-empty cell count, ignoring the goal (io/loader.py::_read_excel, line 158), so the goal was reported unanswerable — and the run still said PASS. And the sizing line announced 99 rows for a sheet with 400, because workload.py::peek (lines 84–85) treats every non-Parquet suffix as CSV and counts newline bytes inside the xlsx ZIP container. It returns estimated=False, so the wrong number is spoken as exact.
